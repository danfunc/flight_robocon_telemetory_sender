# Shizuku 再設計メモ — マルチボード / マルチ ISA

**目的**: 現行 Shizuku (RP2350 / ARMv8-M / pico-sdk に密結合) を、別リポジトリで
「複数ボード・複数 ISA を前提とした構成」へ作り直すための設計資料。

**このメモの立場**: 現行実装の棚卸し + 移植の障壁 + 中核となる設計判断の提案。
実装手順書ではなく、**新リポジトリで最初に決めるべきことの一覧**。

作成日: 2026-08-17 / 対象コミット: `fix/ble-freeze-nonblocking-usb` 系列

---

## 0. 要約

移植性の最大の障壁は ISA 差分そのものではなく、**カーネルがオブジェクト概念を
知っていること**にある。オブジェクト表・メソッド表・特権属性がカーネル本体に
埋まっているため、「ISA 依存の薄い層」を切り出そうとしても中核が一緒に付いてくる。

提案する中核判断は 2 つ:

1. **カーネルからオブジェクト概念を外す** (§3)。カーネルは「保護されたサブルーチン
   呼び出し」「文脈の退避/復帰」「実行権の委譲」の機構だけを持ち、オブジェクト・
   メソッド・権限の意味づけはすべてカーネルオブジェクト側へ。
   → カーネル本体が小さくなり、ISA ごとに書き直す量が激減する。
   → 副次的に `object_table` の 68.5 KB がカーネルから出る。

2. **資源の扱いを 1 つの形に統一する** (§4)。「持つ者が貸す / 外側でクランプ /
   戻りで pop / 超過は超過した者にだけ当たる」。CPU (`run_for`) で実装済みのこの形を、
   メモリ・権限・I/O にも同じ形で適用する。軸ごとに別機構を作らない。

## 1. 現行構成の実測 (移植の出発点)

### 1.1 メモリ (RP2350 / pico2_w, 委譲 ON ビルド)

| 項目 | サイズ |
|---|---|
| `object_table` (`object_t[128]`, うち `method_table[128]` が本体) | **68.5 KB** |
| lwIP `PBUF_POOL` (SDK 側) | 35.9 KB |
| `md_table[128][16]` | 16.0 KB |
| `g_context_pool` (`context_t[128]`) | 16.0 KB |
| `obj_mem[128][16]` | 8.0 KB |
| `thread_table` (`thread_t[128]`) | 6.0 KB |
| ヒープ残 | 283.8 KB |
| スレッドスタック | 8 KB × 実在スレッド数 (~15) = ~120 KB |

**固定 128 幅の表が支配的**。実使用はオブジェクト ~15 / メソッド数個なので、
これらは「使用量に比例しない事前確保」= 予算・会計の対象にならない。
新リポジトリでは**最初から疎な構造**にすること (§5.3)。

### 1.2 呼び出しフレーム (2026-08-13 に変更済み、実機 PASS)

呼び出しの退避先は**スレッド自身のスタック**。共有アリーナ (105 KB) は廃止済み。
幾何は `include/kernel.hpp` の `call_frame_hdr_t` コメントを参照。要点:

- 退避域 `[X-total, X)` の一番上に**元の例外フレームがそのまま残る** → 1 バイトも動かさない
- 下へ複製するのは書き換え用の作業コピーだけ
- FP 活性時のみ S16-S31 の枠を予約 (`has_fp`)、幾何は記録値を読み戻して使う
- 溢れは PSPLIM が UsageFault で捕まえる (深さ上限の panic が不要になった)

**この設計は ISA に強く依存する** (例外フレーム形状 / スタック方向 / スタック上限
レジスタの有無)。移植時の最重要ポイントの一つ (§5.2)。

## 2. ISA / ボード依存の棚卸し

### 2.1 ISA 依存 (ARMv8-M 固有)

| 箇所 | 内容 | 他 ISA での対応 |
|---|---|---|
| `svc_asm_handler.S` | `CTX_SAVE`/`CTX_RESTORE`。`.cpu cortex-m33`, `.fpu fpv5-sp-d16` | 全面書き直し。**ISA ごとに 1 ファイル** |
| 例外フレーム | 基本 32B / FP 拡張 104B、`EXC_RETURN` bit4 で判別、**xPSR bit9 の 8B パディング** | 形状もサイズも別物。抽象化必須 |
| `EXC_RETURN` | 復帰モード + FP 有無をエンコード | ARM 固有の概念。RISC-V には無い |
| `PSPLIM` | スタック下限のハード検出 | **ARMv8-M のみ**。ARMv7-M / RISC-V には無い → ソフト検査へ縮退 |
| `CONTROL.nPRIV` | 非特権実行 | RISC-V は U-mode、ARMv7-M も CONTROL あり。概念は共通、レジスタは別 |
| 遅延 FPU (S16-S31 の手動退避) | `vstmia`/`vldmia` | FPU の有無・レジスタ数・遅延スタッキングの有無が全部違う |
| MPU (PMSA) | `mpu_hw`, region 8 本程度 | RISC-V は PMP。region 数も意味論も違う |
| SysTick + PendSV | 時限実行権の期限回収 | RISC-V は `mtimecmp` + software interrupt |
| `svc` 即値 | API 番号を命令の即値に埋める | RISC-V `ecall` に即値は無い → **レジスタ渡しへ変更が要る** |
| LDREX/STREX (`std::atomic`) | claim の CAS。RP2350-E2 で SIO spinlock が使えない | ISA ごとの atomic |

**`svc` 即値ディスパッチは移植性の観点で要再検討**。現行は「即値 != 0 なら即値が API
番号」というハイブリッド ABI。RISC-V の `ecall` には即値が無いので、番号はレジスタで
渡す設計に寄せた方が共通化しやすい (性能差は要実測)。

### 2.2 ボード依存 (pico-sdk / RP2350 固有)

| 箇所 | 内容 |
|---|---|
| `get_core_num()` / `pico_multicore` | コア識別・core1 起動 |
| `time_us_64()` / `repeating_timer` | 時刻・ビーコン |
| DMA (`hardware_dma`) | ストリーム接続ポンプ (`connect(src,dst)`) |
| I2C / PWM / PIO (WS2812) | ドライバ側 |

| CYW43 / BTstack | BLE。pico2_w のみ (pico2 は `SHIZU_PICO2_TEST` で除外) |
| boot2 / XIP / UF2 / picotool | フラッシュ・書き込み |
| `panic_ring` / `svc_trace` の `__uninitialized_ram` | noinit RAM。**BOOTSEL で消える** (§7) |

### 2.3 ★クロック変更と分周の連鎖 [実測 2026-08-17]

`clk_sys` を変えると、**それを分周して使う全ペリフェラルが影響を受ける**。厄介なのは
SDK 内に「`clk_sys` から動的に算出するもの」と「**固定分周をハードコードしているもの**」が
混在していることで、後者が黙って壊れる。

RP2350 を定格 150MHz → **300MHz** にした実測で、固定分周が 2 件見つかった:

| 依存 | 既定 | 300MHz での症状 | 対処 |
|---|---|---|---|
| `PICO_FLASH_SPI_CLKDIV` (boot2_w25q080) | **2 固定** | フラッシュが 150MHz = W25Q080 定格 (133MHz) 超過 → **XIP からのコード読み出しで落ちる** | 4 に上げる (75MHz) |
| `CYW43_PIO_CLOCK_DIV_INT` | **2 固定** (`clk_sys` から算出しない) | CYW43 の SPI が 2 倍速 → **チップ無応答**。HCI が上がらない | 4 に上げる |

**自動で追従したもの**: UART ボーレート (`clk_peri` から算出。ただし**クロック変更は
`stdio_init_all` より前**に行う必要がある)、I2C / PWM (SDK が算出)、USB
(PLL_USB の 48MHz なので影響なし)、カーネルの µs 換算 (`clock_get_hz(clk_sys)` から取得)、
SysTick のチャンク継ぎ (1 チャンク上限が 111ms → 56ms に縮むが期限は不変)。

**未確認**: PIO を使う他のもの (WS2812 等) も同じ性質を持つ。

> **移植への含意**: **`board` 層が「クロックを変えたら追従が必要な分周」を列挙して
> 保持する**こと。分周が固定値でハードコードされている依存は board 層の責務であり、
> 「`clk_sys` を変える」操作を board 層の API にして、その中で全部を面倒見る形にする。
> 上位 (kernel / objects) がクロックを直接触れる設計にすると、必ずこの穴を踏む。

> **★検出の難しさ**: CYW43 の故障は **`ble_poll` (ポーリング回数) は前進し続ける**
> ため「動いている」ように見えた。壊れていたのは `evt` (チップが上げた実イベント) で、
> 68 → **1** で停止していた。**生存カウンタは機能の証拠にならない** (§7)。

## 3. 中核判断 1: カーネルからオブジェクト概念を外す

### 3.1 現状: カーネルが `object_table` を触る箇所

| 用途 | 現行 | externalize 後 |
|---|---|---|
| 経路判定 (`state == KERNEL_OBJECT`) | オブジェクト種別で分岐 | **信頼された活性化か の 1 ビット**。カーネルは登録済みハンドラ entry だけ知る |
| メソッド解決 (`method_table[m]`) | カーネルが表引き | プリミティブを `CALL(entry_pc, …)` に変更。解決はカーネルオブジェクト |
| current object の張り替え | カーネルが `object_id` を保持 | フレームに**不透明な cookie** を積み、戻りで返すだけ。中身は解釈しない |
| 特権 (`control_for_object`) | オブジェクト属性から導出 | `CALL` の引数で特権を渡す。**強制はカーネル、方針はカーネルオブジェクト** |
| 呼び出し元 identity | `stack_frame->r0 = current_object` | カーネル支援不要。カーネルオブジェクトが自分の記録を読む |
| PendSV の切替延期判定 | `state == KERNEL_OBJECT` なら延期 | 同じ 1 ビットに読み替え |

### 3.2 externalize 後のカーネル ABI (提案)

カーネルが**知っていること**:
- スレッド / 文脈 / スタック / スタック上限
- 呼び出しフレームの push/pop (cookie + 特権 + 戻り先)
- 登録済み svc ハンドラの entry pc + 「信頼活性化中」フラグ
- スケジューリング機構 (claim / switch / 時限委譲)
- MPU region (書けるのはカーネルだけなので機構として保持)

カーネルが**知らないこと**:
- オブジェクト、オブジェクト ID、メソッド表、export、md、svc ルート

**「全部カーネルオブジェクトを経由する = カーネルオブジェクトが肥大する」ではない。**
経路 (routing) と実装 (implementation) は別物:
- **経路**: 全 syscall がカーネルオブジェクトのハンドラを通る。中身は表引き + 再ディスパッチで O(1)、コードは数十行
- **実装**: 各サブシステムの syscall 本体は当該オブジェクト側にあり、REDISPATCH で到達する

むしろ**現行のカーネルオブジェクトの方が大きい** — obj_api の全 API (ストリーム制御 /
grant / affinity / メモリ / md …) が 1 つの巨大 switch に同居している。委譲は特権を
渡さなくてもこれを外に出せるので、**カーネルオブジェクトは縮む**。

残る本当のコストは肥大ではなく**単一障害点**: カーネルオブジェクトは全 syscall の
クリティカルパス上にある。だからこそ「ルータに徹して副作用を持たない」形に保つこと。

プリミティブの骨格 (名前は仮):

```
CALL(entry_pc, cookie, priv, args…)   // 保護されたサブルーチン呼び出し
RETURN(n, value, err, depth_claim)    // n 段巻き戻し。depth_claim は検算用
SET_HANDLER(entry_pc)                 // svc トランポリンの宛先
SWITCH(tid) / GRANT(tid, budget)      // 実行権
```

### 3.3 これが移植性に効く理由

ISA ごとに書き直す必要があるのは「文脈退避 / 例外フレーム / 特権遷移 / タイマ」の層
だけになる。オブジェクトモデル・メソッド呼び出し・委譲・md は**全 ISA 共通の C++**
としてカーネルオブジェクト側に残る。現行は中核にオブジェクト概念が埋まっているため、
この分離ができない。

### 3.4 【決定】信頼ビットは 1 個。サブカーネルに特権は渡さない

当初「委譲サブカーネルが特権を持てないと往復オーバーヘッドが出る」を最大の論点と
していたが、**overhead を払う**方針で決着 (2026-08-17)。

**根拠**:
- **高頻度パスは既に syscall の外にある**。ストリームのデータプレーン (`push`/`pop`)
  は SVC を通らないライブラリで、`connect(src,dst)` はカーネル専有 DMA ポンプ。
  syscall が乗るのは**制御プレーンだけ**で元々低頻度。「特権が無いと遅い」が効くのは
  高頻度に syscall を撃つ設計の場合だが、この系はそう作られていない。
- **実測**: 委譲サブハンドラが特権ゼロで 6 段ネスト (トランポリン + REDISPATCH の
  計 14 枚を往復) を回して util 不変 (core0 7.0% / core1 52.8%)。呼び出しフレームは
  スレッドスタック上なので確保も走らない。
- **サブカーネル自身がシステム資源を使い潰せると、そもそも会計が成立しない。**
  「このオブジェクトが X 使った」と言えるのは、会計係を迂回できないときだけ。
  特権を配ると資源管理の前提が壊れる。
- 現行の穴 (`in_handler && to_kernel_primitive` による**無制限の昇格**、
  `SET_SVC_HANDLER` で syscall 乗っ取り可能) は貸し出しが無制限だったことが原因。
  **貸し出しゼロなら同種の穴は構造的に存在しない**。

**特権を渡さなくても委譲に残る価値** (委譲機構自体は維持する):
- **方針の局所性** — サブシステムの syscall 意味論が中央の巨大 switch ではなく
  当該オブジェクト側に置ける
- **発行元 identity が保たれる** — 委譲経路は本当の発行元が見える。中央経路
  (`METHOD_CALL`) はこれを潰してカーネルオブジェクトに化けさせる (§ 付録)

つまり特権は性能のための後付けであり、外した方が本来の目的 (機構と方針の分離) に忠実。

**残る確認事項**: サブカーネルが管理対象に対して原子的にやりたい操作がある場合、
カーネルオブジェクトを往復する間にプリエンプション点が入る。現行は PendSV が
「信頼活性化中は切替を延期」する作りなので概ね吸収されるが、**サブカーネル活性化中も
延期対象に含めるか**は決めておくこと。

## 4. 中核判断 2: 資源の扱いを 1 つの形に統一する

普通のカーネルは軸ごとに別機構を持つ (スケジューラクラス / capability ビット /
cgroup / LSM)。Shizuku の主張は **1 つの形を軸を変えて繰り返す**ことにできる:

> **持つ者が貸す / 外側の値でクランプ / スタックに積み戻りで pop /
> 超過は超過した者にだけ当たる (系は死なない)**

| 軸 | 現状 |
|---|---|
| CPU | `run_for` / grant スタック — **実装済み・実機検証済み** |
| メモリ (実行時) | PSPLIM = grant deadline のメモリ版 — 呼び出しフレームのスタック退避で実現 |
| メモリ (データ) | オブジェクト arena — 未着手 |
| **権限** | **貸し出さない方針で決着 (§3.4)。この軸は作らない** |
| I/O | TX 優先度ストリーム — 構想のみ |

**権限を静的クラス (`SYSTEM` / `SUBSYSTEM` などの enum) で表すのは避ける。**
それはリングモデルであり、カーネルの中に権限マトリクスができて
「機構はカーネル、方針はオブジェクト」が崩れる。

代わりに **`REDISPATCH(entry, cookie, 貸す権限のマスク)`** の形にする:
貸し手が明示し、カーネルは**貸し手が持つ範囲でクランプして覚えるだけ**、
戻りで自動的に消える。`GRANT_CPU` が外側 deadline でクランプするのと同型。
撤回もできる (静的クラスにはできない)。

**ただし 2026-08-17 に「権限は貸し出さない」で決着した (§3.4)** ため、この形を権限軸へ
適用する予定は当面ない。ここに書き残すのは、将来 overhead が実測で問題になったときの
**唯一の正しい拡張方向**として。静的クラス (`SYSTEM` / `SUBSYSTEM` の enum) を足すのは
リングモデルであり、カーネル内に権限マトリクスを作って設計原則を壊すので選ばないこと。

当面は「貸し出しゼロ」+ カーネルが記録した**偽装不能な発行元**による検査で足りる。

## 4.5 巻き戻し規律 — 「どこまで戻るか」を誰も判断しない形にする

全 syscall がカーネルオブジェクトを経由する構成 (§3.4) では、スレッドの呼び出しスタックに
積まれるフレームは 3 種:

- **SVC_ENTRY** — トランポリン (非信頼 → カーネルオブジェクトのハンドラ)
- **REDISPATCH** — カーネルオブジェクト → サブシステムのハンドラ
- **CALL** — メソッド呼び出し

### 規律: フレームを積んだ層が、その 1 枚だけを落とす

**戻る側は「どこまで」を判断しない。** サブシステムのハンドラは、自分と元の発行元の
間に何枚挟まっているかを知らないし、知る必要もない。自分の呼び出し元
(= カーネルオブジェクト) に値を返すだけ = **1 枚**。

カーネルオブジェクトは REDISPATCH を撃った当人なので、戻ってきた時点で
「自分のトランポリン枠も落とす」ことを自分の帳簿から知っている。だから最後の 1 枚も
自分で落とす。**総数を計算する主体がどこにも要らない。**

これが成立する条件は 1 つだけ:

> **フレームを push した層が、必ずその層で pop する (フレームの所有権)。**

`RETURN(n, …)` の `n` は ABI としては任意段数を許すが、**正常系では常に 1**。
そして発行側が申告する「今のネスト数」(§付録) が、この所有権不変条件の検査になる —
他人のフレームを落とそうとすると申告した深さと実際が食い違って弾かれる。

### 任意段数 (n > 1) が本当に要るのは異常系だけ

| ケース | 誰が数えるか |
|---|---|
| **異常系の巻き戻し** (フォールト / 予算超過で活性化の連鎖を畳む) | 連鎖を**所有している側** (カーネル or カーネルオブジェクト) が自分の帳簿から数える。戻る側は関与しない |

正常系で「どこまで戻るか」を判断する主体は存在しない。**所有権の規律だけで足りる**
(各層が自分の 1 枚を落とす)。

### ★末尾委譲 (フレーム置換) は既定にしない

REDISPATCH がフレームを **push** せず **置換** すれば、戻りは発行点へ直行して
中間層は関与しなくなる — が、**これは採らない**。

委譲した層が二度と制御を取り戻さないので、その層は:
- サブシステムのエラーを呼び出し元の ABI へ**翻訳できない**
- 失敗したことを**知ることすらできない**
- 後始末・リトライ・フォールバックが**できない**
- 資源の使用量を**記録できない**

そして §3.4 の決定と矛盾する。「サブカーネルに特権を渡さず overhead を払う」を選んだ
理由は**カーネルオブジェクトを迂回させないことで会計を成立させる**ためだった。
末尾委譲は**戻り経路の迂回**であり、行きだけ通して帰りを通さないなら、払った overhead の
見返りを自分で捨てることになる。

**実例**: 2026-08-13 に修正した握り潰しバグ — REDISPATCH の戻り値 (エラーコード) を
見ずに値だけ流しており、失敗時に担当オブジェクト ID が「成功した戻り値」に化けていた。
**戻ってくる設計だったから直せたバグ**で、末尾委譲なら直しようがない。

→ **既定は call (必ず戻る)**。末尾委譲を使うなら「この層は戻り道でのエラー処理と
会計を放棄する」という明示の例外として扱い、段数を減らす手段として正当化しないこと。

### ★exit は REDISPATCH (フレーム置換) で実装する

上で「末尾委譲 = フレーム置換は既定にしない」としたが、**exit だけは例外**であり、
むしろ置換で実装すべき。理由は単純で、**exit は定義上その先が無い**ので、
「戻り道でのエラー処理と会計を失う」というコストが原理的に発生しない。

これで 3 つの問題が同時に閉じる:

| 問題 | 解 |
|---|---|
| 戻り口の自己参照 (+1 ずれ) | 置換なので**フレームが増えない** |
| 誰が段数を数えるか | **数えない**。各層は「自分の活性化を終える」と言うだけ |
| ハンドラの特権昇格 | exit は **self-limited** なので全オブジェクトに開放しても昇格でない |
| 他人のフレームを落とせないか | **ネスト数の申告 = 所有権検査**が防ぐ |

**特権の観点が重要**: exit の blast radius は自分のフレームだけで、`SET_SVC_HANDLER`
のように他者に対する権限を得るわけではない。2026-08-13 に削除した穴の本当の誤りは
「exit を露出したこと」ではなく **200..206 を塊で露出したこと**だった。個別に見れば
exit だけは安全に開放できる。**条件は所有権検査 (ネスト数の申告) が効いていること**。

これにより「どの層まで戻るかを指定する API」という問題設定自体が消え、
**「自分の活性化を終える操作」**に作り替わる。

### 自己参照の閉じ込め (置換で実装しない場合の退避策)

「戻るための syscall 自身がフレームを積む」ため段数が +1 ずれる問題は、
**`RETURN` をフレームを積まないカーネルプリミティブにする**ことで消える。
これができない構成 (RETURN もトランポリンに乗る) でも、+1 を知っているのは
**カーネルオブジェクトの 1 箇所だけ**にできる。現行実装が壊れやすかったのは、
この +1 を各呼び出し元がハードコードしていたため (`arg1=1` = 2 枚が散在していた)。

## 4.6 委譲ファミリ — REDISPATCH 1 種類では足りない

現行の委譲の道具は `REDISPATCH_SVC` だけで、「サブシステムが svc **番号の範囲**を
丸ごと引き受ける」形しかカバーしていない。代償として**委譲先がハンドラ ABI**
(`svc_handler_shim<F>`: r0..r3 引数 + svc番号 / 発行元 / thread / ネスト数を
callee-saved で受ける) を実装しなければならず、ただメソッドを公開したいだけの
サブシステムには重い。

かといって `METHOD_CALL` を使うと**発行元 identity が潰れて中継者 (カーネル
オブジェクト) に化ける**。→ 現状は「identity を取るか、普通の ABI を取るか」の二択。

### ★カーネルプリミティブとしては 2 種類。3 形態はその上の方針

identity は**カーネルが導出する値ではなく、カーネルオブジェクトが渡す不透明な
パラメータ**にする。理由は §3 の帰結:

- オブジェクト概念を持たないカーネルは「発行元オブジェクト」を**導出できない**
- 一方カーネルオブジェクトは current object を自分で持っているので、トランポリン
  された瞬間に自分の帳簿を読めば分かる
- 偽装の懸念は無い。**そのプリミティブを撃てるのはカーネルオブジェクトだけ**で、
  それは信頼境界そのもの (嘘をつくなら全部終わりなので新しいリスクは増えない)

したがってカーネル側は 1 本にまとまる:

```
CALL(entry_pc, callee_cookie, caller_cookie, priv, args…)
```

カーネルは `caller_cookie` を呼び先のフレームへ載せるだけで**中身を解釈しない**。
下表の 3 形態は「カーネルオブジェクトが caller_cookie に何を入れるか」という**方針**に
落ちる (元の発行元 → strict / 自分 → 中継者)。**機構はカーネル、方針はカーネル
オブジェクト**がここでも成立する。

→ **委譲のカーネルプリミティブは REDISPATCH と CALL の 2 種で足りる。**

**副次効果**: identity をカーネルが記録しなくてよくなるので、`inv_svc_num` /
`inv_caller_obj` / `inv_caller_thread` が **context_t からも呼び出しフレーム
ヘッダからも消える** (16B × context 数 + フレームごと)。REDISPATCH は必要な情報を
引数で受け取るだけになる。

**★注意**: この設計は「カーネルオブジェクトが caller_cookie を正直に埋める」ことに
全面的に依存する。信頼境界なので設計上は問題ないが、**間違えても静かに壊れる**
(identity が黙って化ける) — 2026-08-13 に踏んだ REDISPATCH の引数バグと同型。
**自己テストに identity の end-to-end 検証を必ず残すこと** (現行 svc_delegate_test の
`caller(a=28 b=27)` 突き合わせ。あれが無ければ当該バグは見つかっていない)。

### 3 形態 (カーネルオブジェクト側の使い分け)

| | 入る ABI | identity | 用途 |
|---|---|---|---|
| **REDISPATCH** | ハンドラ (元の syscall そのまま) | 元の発行元 | syscall 番号の範囲を引き受けるサブカーネル |
| **CALL_STRICT** ★欠けている | メソッド (普通の export) | 元の発行元 | メソッドを公開するだけのサブシステム |
| **CALL** (現行) | メソッド | 中継者 | カーネルオブジェクトが自分の都合で呼ぶとき |

4 つ目のマス (ハンドラ ABI + 中継者 identity) は意味を持たない — 生の syscall を
転送するのに発行元を偽る理由がない。**2×2 の 1 マスが空で実質 3 種類**。

### 既定を入れ替えること

現行 `CALL` は identity が**黙って** 0 (カーネルオブジェクト) になるので、呼ばれた側は
誰に呼ばれたか知る手段が無く、しかもそれに気づけない。**オブジェクトが自前の
アクセス制御を持てない根本原因**がこれで、資源管理 (誰の勘定に付けるか) の前提も崩す。

→ 新リポジトリでは **`CALL_STRICT` を既定**にし、identity を落とすのは
「中継者として振る舞う」という**明示指定**にする。現行で呼び出し元 identity を
実際に使っているドライバは見当たらないので、入れ替えコストはほぼゼロ。

## 5. 新リポジトリの層構造 (提案)

```
arch/<isa>/        文脈退避・例外フレーム・特権遷移・atomic・タイマ割り込み
                   (armv8m / armv7m / riscv32 …)  ← ISA ごとに書き直す唯一の層
board/<board>/     コア起動・時刻・UART/USB・DMA・ペリフェラル
                   (rp2350_pico2w / rp2350_pico2 / …)
kernel/            スレッド・文脈・呼び出しフレーム・実行権委譲
                   ★オブジェクト概念を持たない (§3)
kobj/              カーネルオブジェクト: オブジェクト表・メソッド解決・
                   svc ルート・md・スケジューリング方針  ★全 ISA 共通
objects/           ドライバ / アプリ
```

### 5.1 `arch` が提供すべき抽象 (最小)

- 文脈の退避/復帰 (callee-saved + スタックポインタ + 復帰情報)
- 例外フレームの**サイズと位置**の問い合わせ (FP 拡張・アライン padding 込み)
- 呼び出しフレームの push/pop に必要な幾何計算
- 特権レベルの設定 / 現在値
- スタック上限の設定・検査 (ハード or ソフト)
- atomic CAS
- 時限割り込みの装填 / 強制切替の起票

### 5.2 移植で最初に壊れるところ

**呼び出しフレームの幾何** (§1.2)。ARMv8-M では

- 例外フレームサイズが FP 有無で 32/104 と変わる
- **xPSR bit9 のパディングで復帰時 SP が +4 される**
  → 見込まないと退避域を踏み潰して**無言ロックアップ**する (実際に踏んだ)

他 ISA では別の落とし穴が必ずある。**`arch` 層に「例外フレームの実サイズ」と
「復帰後の SP」を問う関数を置き、カーネルはそれしか使わない**設計にすること。

### 5.3 最初から疎にすべき表

`object_table` / `md_table` / `obj_mem` を `[128][N]` の固定配列にしない。
使用量に比例しない事前確保は**予算・会計の対象にならない**ので、
資源管理を設計に入れるなら疎構造が前提条件になる。

### 5.4 実装は template + concepts で

`arch` / `board` の差し替えを**仮想関数ではなくコンパイル時の型パラメータ**で行う。
カーネルは 1 バイナリ 1 ISA なので実体化は 1 つ、コード膨張も間接呼び出しも発生しない。

```cpp
template <class A> concept Arch = requires(typename A::context_t &c) {
  { A::exc_frame_bytes(c) } -> std::same_as<uint32_t>;  // 例外フレーム実サイズ
  { A::psp_after_return(c) } -> std::same_as<uintptr_t>; // 復帰後 SP (§5.2)
  { A::set_priv(c, bool{}) };
  { A::stack_limit_set(c, uintptr_t{}) };
  …
};
template <Arch A> class kernel { … };
```

**concepts をセットにするのが重要**。テンプレート化は診断が壊滅しがちだが、
要件を concept で明示しておけば「この ISA バックエンドは
`psp_after_return` を実装していない」と 1 行で出る。現行コードも既に
`svc_handler_shim<T>` / `export_method<T>` が `requires std::invocable<…>` を
使っており、方向としては連続している。

**とくに §5.2 (例外フレームの幾何) は concept で縛ること。** xPSR bit9 の
パディングのような ISA 固有の落とし穴は「関数を用意し忘れる」形ではなく
「用意したが意味が違う」形で入り込むので、**返す値の意味を doc コメントで縛り、
arch ごとに同じ自己テストを通す**こと (§7)。

### 5.5 ビルドシステム — Bazel が有望

判断材料は別リポジトリ `geo_sports` の実測 (`言語比較_引き継ぎ.md`)。
同一機能を Python / Rust / C++(Bazel) / Swift(SwiftPM) で実装して比較したもの。

| | フル(自分) | **差分** | フル(依存込み) |
|---|---:|---:|---:|
| Rust `--release` (fat LTO) | 13.23 s | 15.34 s | 25.5 s |
| Rust `--profile quick` | 2.84 s | 2.85 s | 15.7 s |
| **C++ (Bazel)** | 4.45 s | **0.88 s** | **13.6 s** |
| Swift (SwiftPM) | 7.63 s | 5.61 s | 35.7 s |

**差分ビルドの速さはコンパイル単位の粒度で決まる** — C++ は翻訳単位ごとなので差分が
フルの 1/5、Rust はクレート全体が単位なので差分 = フル。また C++ は ThinLTO なので
**LTO を切らずに済む** (Rust の fat LTO / Swift の WMO は差分ビルドを 5〜17 倍に膨らませる)。

この差はカーネル開発で直接効く: 今日 (2026-08-13) の作業では 7 構成 × 十数回の
ビルドを回した。差分が 0.88 s か 5 s かは体感が変わる。

**Bazel を推す本当の理由は再現性の方**。geo_sports では Bazel が第三者依存を
ソースからビルドして静的リンクするため zlib 1.3.1 に固定できた一方、SwiftPM は
`systemLibrary` がシステムの libz 1.2.12 を指すため**揃えられなかった**
(性能差の一部がそこに由来すると見積もられている)。

現リポジトリの痛点と正確に対応する:

| 現状 (CMake) | Bazel なら |
|---|---|
| `$ENV{PICO_SDK_PATH}` に依存。export しないと configure が落ちる | 依存を宣言して固定。環境変数に依存しない |
| 構成ごとに `build_*` ディレクトリを手で作り `-DSHIZU_*` を渡す (7 個並存) | 構成 = target。**全構成を 1 コマンドでビルド/テスト** |
| `SHIZU_*` トグルが 15 個以上、組み合わせが掛け算で爆発 | `select()` + `config_setting` で構造化 |
| 構成間の非対称が検出されない (`build_mcdc` が壊れたまま気付かれていなかった) | CI で全 target を回せば即検出 |
| ISA/ボードごとのツールチェーン切り替えが CMake の分岐頼み | **toolchain rule が本来の用途**。multi-ISA と正面から噛み合う |

### 5.6 【推奨】C++ (template + concepts) + Bazel

**理由 1: Bazel に決めるなら Rust は二重管理になる。**
`rules_rust` の依存解決 (`crate_universe`) は**内部で実際に cargo を走らせて**
lockfile を解決し BUILD を生成する。加えて組込みでは `no_std` ターゲットの
`core`/`alloc` 再ビルド (`-Z build-std`) が nightly + cargo 前提で、Bazel 下に
持ち込むのが面倒。`build.rs` を持つクレートも二重管理になる。
→ **Rust + Bazel = ビルドシステム 2 つ**で、継ぎ目が一番痛い箇所に来る。
C++ + Bazel なら 1 つ。

なお Bazel に期待していた「依存をソースから固定し環境に依存しない」は、
**純 Rust なら cargo (Cargo.lock + vendoring) でも相当できる** → 純 Rust なら
Bazel の旨みは薄い。しかし**この系は純 Rust にならない** (pico-sdk / tinyusb /
btstack / cyw43-driver は C)。混在こそ Bazel の土俵だが、そこへ Rust を混ぜると
上記の二重管理を必ず踏む。

**理由 2: カーネルの一番難しい部分は Rust の型システムが守らない。**
2026-08-13 に何時間も溶かしたバグの内訳:

| バグ | Rust で防げたか |
|---|---|
| REDISPATCH が元 syscall の r0..r3 を渡していない | ❌ 生の例外フレームを触る `unsafe` の中身 |
| ハンドラ shim の第 8 引数が r12 を名乗って実体は r7 | ❌ 手書き asm の push 順と AAPCS の対応 |
| xPSR bit9 パディングで復帰後 SP が +4 され退避域を踏む | ❌ ハードウェアの ABI 幾何 |

全て「生のハードウェア ABI の幾何」で、言語を変えても `unsafe` の中に残る。
Rust が効くのは上の層 (オブジェクト表 / ストリームバッファ / ドライバ) で、
所有権とライフタイムが実際に仕事をするところ。

**理由 3: 実機で詰めた部分がそのまま残る。** 呼び出しフレームの幾何 (§1.2) は
実機で通ったばかりで、書き直しは高い。

**理由 4: Rust は後から足せる。** この系は **svc + メソッド呼び出しという安定 ABI
境界**を持つので、ドライバ層だけ Rust にするのは後日でも成立する。
**「コアを C++ で書いて後から Rust オブジェクトを足す」は安いが、
「検証済みのカーネルコアを Rust へ書き直す」は高い** — 片方向にしか安くないので、
C++ が後悔の少ない選択。

## 6. 移植順序 (提案)

1. `arch` 抽象を定義し、**ARMv8-M で現行と同等**に動かす (退行なしを確認)
2. カーネルからオブジェクト概念を外す (§3)。ここまでは 1 ISA で完結
3. 2 つ目の ISA を追加 (推奨: ARMv7-M — PSPLIM 無し / FP 差分だけで済み、
   RISC-V より落差が小さい)
4. RISC-V を追加。`ecall` に即値が無い問題 (§2.1) をここで解決
5. ボード追加 (pico2 / pico2_w は既に `SHIZU_PICO2_TEST` で分岐実績あり)

## 7. 検証インフラ (現リポジトリで確立済み。新リポジトリでも最初に用意すること)

移植中は「無言で固まる」が常態になる。以下は実際に何時間も溶かして得た教訓。

- **段階的な自己テスト**: いきなり多段ネストを試さない。
  「1 段の最小プローブ → 2 段 → N 段」の梯子を用意する。
  6 段で一気に確かめようとして、1 段目の不具合と往復の不具合を区別できず長時間を失った。
  最小プローブに落とした瞬間に原因 (引数が化けていた) が即座に見えた。
- **固まっても出力が出る経路**: printf がリングバッファ経由だと、系が固まると
  **panic すら表に出ない**。タイマ割り込みから「リング滞留が前回と同値なら同期排出」
  する救出経路を最初から入れる。
- **書き込みの完了判定**: 固まったファームは書き込みツールのリセット要求を処理できず、
  ツールは**成功終了コードのまま書き込まずに終わる**ことがある。
  完了を示す出力行の有無で判定すること (これを見落として切り分け結論を丸ごと間違えた)。
- **noinit RAM のトレースは万能ではない**: BOOTSEL で消えることがある
  (bootrom が SRAM 下位を使う)。「固まっても次のブートで読める」は経路次第。
- **焼く前にシリアルキャプチャを張る**: 起動直後の同期排出はホストがポートを
  開く前に流れて落ちる。ポート出現の瞬間に開く待ち受けを先に起動しておく。

## 8. 新リポジトリで最初に決めること

1. ~~信頼ビット 1 個で行くか、貸し出しを入れるか~~ → **決着済み (§3.4)。1 個で行く**。
   残るのは「サブカーネル活性化中も PendSV の切替延期対象にするか」だけ
2. **svc 番号の渡し方**: 即値ハイブリッドを維持するか、レジスタ統一にするか (§2.1)
3. **スタック上限**: PSPLIM 相当が無い ISA でどう縮退させるか (ソフト検査 / ガードページ相当)
4. **`arch` の粒度**: 例外フレーム幾何をどこまで抽象化するか (§5.2)
5. **委譲ファミリの粒度** (§4.6): REDISPATCH / CALL_STRICT / CALL の 3 種で足りるか。
   非同期 (別スレッドへ手渡す) 形が要るかは用途が出てから
6. **ビルドシステム** (§5.5): Bazel 化を先にやるか、CMake のまま移植を進めるか
7. **クロック変更の API 化** (§2.3): 分周の追従を board 層に閉じ込めるか、
   固定クロック前提にするか
8. ~~実装言語~~ → **C++ (template + concepts) を推奨 (§5.6)**。Rust はドライバ層に
   後から足せる (安定 ABI 境界があるため)
8. **md を作り直すか**: 認可の償却パスとしての意図は正しいが、償却する認可が実在して
   から。現行実装は移植しないこと (呼び出し元索引でない / 半端 / 利用者ゼロ)

## 付録: 現行で解決済み・引き継ぐべき知見

| 事項 | 内容 |
|---|---|
| 巻き戻しの ABI | 段数は任意のまま、発行側が「今のネスト数」を申告しカーネルが実際の深さと突き合わせる (両側チェック)。合わなければ 1 段も落とさずエラー |
| 戻り口 | フレーム種別ごとにカーネルが `lr` を載せる。信頼側と一般側で別の戻り口が要る (混ぜると特権の穴になる) |
| 委譲時の引数 | 再ディスパッチは**元の syscall の引数を復元して**サブハンドラへ渡すこと。忘れると引数が担当オブジェクト ID に化け、終了条件に到達せず無限再帰する |
| ハンドラの ABI | 呼び出し情報を callee-saved レジスタで渡すシムは、push 順と引数位置の対応を間違えやすい (第 8 引数が r12 のつもりで実体は r7 だった) |
| panic 禁止 | 段数・予算の申告ミスは**申告した者だけ**を止める。記録は残し、系は生存させる |
| 呼び出し元 identity | 現行の `METHOD_CALL` は呼び出し元をカーネルオブジェクトに化けさせる。オブジェクトが自前のアクセス制御を持てない根本原因 |
