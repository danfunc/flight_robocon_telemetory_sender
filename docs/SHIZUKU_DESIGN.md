# 第 I 部 なぜこう作るのか

## 1. 問題意識 — 修正の波及

Shizuku の研究課題は **「修正の波及が起こりにくいカーネルの開発」**。

修正の波及とは、ある機能を追加・修正するときに、**目的以外の機能まで考慮・修正
しなければならなくなる**現象。これが起きると:

- 初学者が学習すべき範囲が際限なく広がる
- 既存コードの修正量が新規機能の試作を制限する
- 結果として、カーネルを基盤に成り立つ情報社会の持続的な開発が妨げられる

**あらゆる分野・レイヤーで誰もが気軽に試行錯誤しながら開発できる状態**を作るには、
波及を構造的に抑える必要がある。以下の設計判断はすべてこの一点から導かれる。

### 1.1 モノリシックカーネルの不自由さ

UNIX/POSIX 系の「全てはファイルである」は、fd を通じて**多態性**を与える。同じ
バイナリが実行時に別のファイル (デバイス / 設定) に対して動く。

しかしこの恩恵を受けられるのは**ファイルシステムという概念上で動くプログラムだけ**で、
デバイスドライバは受けられない。USB のようにプロトコルスタックを階層的に組み合わせる
ドライバや、VPN のように既存レイヤーへ上乗せする仕組みを書こうとすると、
**処理を差し込む機構を個別に用意する**ことになり、セキュリティ的にもソースコード的にも
読みにくくなる。

> **結論**: カーネル (最も低い基幹レイヤー) は**最小限の抽象化機構のみ提供**し、
> **組み合わせ**によって様々な機能を実現できるようにするべきである。

### 1.2 マイクロカーネルの無秩序

メッセージパッシングは柔軟だが、**タスクがあらゆる他タスクにメッセージを送れる**。
送信可否の判定はせいぜい「宛先が存在するか」程度。そこに秩序がないため:

- 機能を提供するタスクは、**まずセキュリティ管理タスクへの対応を実装しておかないと**
  不正利用され得る
- 特定のセキュリティモジュールに依存したタスク実装は移植性が低く、そのモジュールの
  API が変わると**タスク側も全部アップデートが必要**になる

つまり**無秩序もまた修正の波及を生む**。薄いカーネルであっても、無秩序なカーネルは
その上で動くソフトウェアの考慮事項を増やす。

> **結論**: カーネルは**適度に自由に、適度に不自由でなければならない**。
> カーネル上に構築された機能に対するアクセス制御を、適切な範囲で行う必要がある。

### 1.3 シグナルの限界 (メソッド呼び出しの原点)

カーネルからプロセスへ能動的に通知する唯一の手段がシグナルだが:

- **実行中の処理に割り込む**形で走るため、排他区間と衝突するとデッドロックする
  (シグナルハンドラ内で malloc/free が使えない)
- 標準動作の追加はカーネル改造が必要
- 種類が少なく GUI に使えないため、**アプリはイベント待ちのコードを書かざるを得ない**
  (論理的に 1 スレッド 1 イベント)

> **結論**: カーネルからソフトウェアを起動すること自体は必要だが、**割り込みではない
> 仕組み**が要る。→ **カーネルがオブジェクトのメソッドを呼べばよい。**
> これが「メソッド呼び出しによるオブジェクト間通信」の原点である。

## 2. 設計原則

原則は 3 つ。以降のすべての機構はこれらから導かれる。

### P1. 機構はカーネル、方針はオブジェクト

カーネルは意味を解釈しない。「どの svc を誰に回すか」「誰が誰を呼んでよいか」
「どの資源をいくら割り当てるか」はすべてカーネルの**外**にある。

これは §1.1 の結論 (最小限の抽象化機構 + 組み合わせ) の直接の実装形。

### P2. 適度に自由に、適度に不自由に

カーネルは**アクセス制御の枠組みを提供する**。ただし枠組みだけで、中身の方針は持たない。
デフォルトは拒否、明示的に許可を積み上げる。

これは §1.2 の結論。無秩序を避けつつ、方針をカーネルに焼き込まない。

### P3. 徹底した分業 — 各オブジェクトは自分の役割だけに集中する

- **デバイスを駆動するオブジェクト**は、デバイスの動作にだけ集中すればよい。
  「操作できる状態にある = 適切なクリアランスが与えられている」とみなしてよい
- **権限管理をするオブジェクト**は、権限管理にだけ集中すればよい。
  対象が実デバイスか仮想デバイスかを考慮しなくてよい

**この分業が成立していること自体が「修正の波及が起きない」の定義**である。
片方を変えても、もう片方が変更を強いられない。

## 3. 設計目標と非目標

### 目標

1. **セキュリティの堅牢性** — アプリケーションに階層構造と通信制限をかけ、
   **アプリ側がセキュリティ的配慮を欠いていても運用で解決可能**にする
2. **開発範囲の限定** — カーネルと、その上のシステムの動作を本来の目的に限定する。
   初学者にも本質を誤魔化さずに説明できる設計哲学を保つ
3. **アプリもドライバも同じ「オブジェクト」として扱う** — 従来別物として実装せざるを
   得なかったものを、少なくともこの体系の上では同一に扱う
4. **イベント待ちのコードを書かせない** — カーネル/他オブジェクトから呼ばれる側になる
5. **複数 ISA / 複数ボード**を前提にする

### 非目標

- 汎用 OS であること (POSIX 互換、動的ロード、ファイルシステムの内蔵)
- スレッド数・オブジェクト数のスケーラビリティ
- プリエンプティブなタイムシェアリング (時限は異常時の安全網であって quantum ではない)

## 4. オブジェクトシステム

ファイルシステムやメッセージパッシングに代わる、仮想 IO・オブジェクト間通信の概念。

### 4.1 原設計の基本ルール (2024) と現状

| # | ルール | 現状 |
|---|---|---|
| 1 | オブジェクトは資源 (CPU 時間・記憶領域) を持つ | 部分的 [実装済] — CPU は grant、メモリは未 |
| 2 | 他オブジェクトから呼べるメソッドを公開できる | [実装済] |
| 3 | 自身が保有する資源を自由に開放できる | [未] |
| 4 | 特権オブジェクトと一般オブジェクトを区別する | [実装済] |
| 5 | **親子関係をつける。子を自由に作成できる** | **[未実装・原設計にあり]** |
| 6 | 特権オブジェクトはカーネルモードでアクセスできる空間に置く | **要再定義 (§11)** |
| 7 | 特権オブジェクトのメソッド呼び出しはカーネルモードのまま処理 | **前提が消滅 (§11.5)** |
| 8 | **基本的に親子のメソッドのみ呼び出せる** | **[未実装・原設計にあり]** |
| 9 | **他オブジェクトのメソッドを表す md を持てる** | 形だけ [未] |
| 10 | md 経由の呼び出しは O(1) | 形だけ [未] |
| 11 | **md に登録されたメソッドは自由に呼び出せる** | **[未実装・原設計にあり]** |

### 4.2 アクセス制御の構造 (ルール 5・8・9・11 の意味)

この 4 つは**一体で 1 つのアクセス制御機構**を成す。バラバラに実装しても意味がない。

```
デフォルト:  親子関係にあるオブジェクトのメソッドしか呼べない  (拒否が既定)
例外:        md に登録されたメソッドは自由に呼べる              (明示的な許可)
付与者:      md を払い出せるのは特権オブジェクト                (方針の所在)
```

> **md への登録 = セキュリティクリアランスの付与**。
> md は性能のための近道ではなく、**権限付与機構そのもの**である。

同様に **親子関係にあること自体が許可証**として働く。子オブジェクトを作れるのは親で、
操作できるのは直接の子まで (孫は操作できない)。これにより、一般オブジェクトが考慮
すべき相手が構造的に限定される (= P3 の分業が成立する)。

> **★用語の注意 (2026-08-17)**: 原設計の「特権オブジェクト」は**3 つの独立した軸**を
> 1 語に束ねている (実行特権 / メモリ到達範囲 / オブジェクト権限)。しかも「カーネル
> 空間に配置する」は MMU 前提の Linux 的モデルの借用で、単一アドレス空間ではそのまま
> 成立しない。**§11 で 3 軸に分解し直す。** ここで言う「特権オブジェクト」は
> **軸 C (オブジェクト権限) のみ**を指すものとして読むこと。

そして特権オブジェクトには全オブジェクトを操作する権利を与える。理由は明快で、
**システム全体のセキュリティ管理を行うオブジェクトが、親子・孫の関係とその制限に
苦悩せずに機能を実装できるようにするため**。そのオブジェクト自身がシステムに悪影響を
与える可能性は考えない (それが起きたらどちらにせよ回復不能と決めつける)。

### 4.3 メリットとデメリット (原設計)

**メリット**
- カーネルがメソッド呼び出しに応じて実行文脈を用意するので、**イベントを能動的に
  待つ状態へ移行しなくてよい**。複数イベントを待つためだけに大量のスレッドを作って
  待機させる必要がない = 資源の節約
- デバイスに対して行える操作を、そのままメソッドとして表現できる
- 階層的アクセス制御があるので、ユーザーへの確認を伴うアクセス制御を容易に提供できる

**デメリット**
- ファイルシステムとは異なる概念なので、アプリもドライバも**この体系の考え方で
  作り直す必要がある**

### 4.4 想定するシステム構成

```
システムオブジェクト        デバイス抽象化 + 権限管理 (Linux のファイルシステム相当)
  └ セッションオブジェクト   キーボード + ディスプレイの対を管理
      └ ユーザーオブジェクト  ユーザーを表す。アプリの要求をシステムへ中継
          └ アプリ
  └ 各種デバイスドライバオブジェクト
```

アプリがカメラ/マイクを要求すると、ユーザーオブジェクトが「ユーザーの許可があるなら」
システムへ中継する。認証情報はセッションオブジェクトから直接取得できるので安全に
認証できる。**特定実行ファイルだけユーザーを変える (setuid) ような仕組みが不要になり、
root の乱用を防げる。**

ファイルシステムもこの上に構築可能で、その操作はメソッド呼び出しを通じて行われる。

# 第 II 部 どう作るのか

## 5. 中核概念

| 概念 | 定義 |
|---|---|
| **オブジェクト** | メソッドの集合と資源の単位。**カーネルは知らない** (§7) |
| **スレッド** | 実行文脈。カーネルが知る唯一の実行単位 |
| **現在オブジェクト** | あるスレッドが「今どのオブジェクトとして」走っているか。カーネルには不透明な cookie として見える |
| **メソッド呼び出し** | 現在オブジェクトを差し替えて、同一スレッド・同一スタック上で別オブジェクトのコードへ移る操作 |
| **カーネルオブジェクト** | 唯一の信頼オブジェクト。オブジェクトモデル・方針・表を全て持つ |

## 6. 実行モデル **[実装済]**

### 6.1 保護されたサブルーチン呼び出し

オブジェクト A が B のメソッドを呼ぶとき、**スレッドもスタックも変わらない**。
現在オブジェクトが A → B に差し替わり (特権もそれに追従)、呼び出し元の文脈は
そのスレッド自身のスタック上に退避される。

> **原設計との差分**: 原設計は「呼び出しごとにカーネルがスレッドを作成する」だった。
> 現行は同一スレッド上の呼び出しに変えてある (§12.3)。

戻り値は 1 語。大きなデータはポインタを渡して呼び先がコピーする (単一アドレス空間)。

### 6.2 syscall の受け方

**経路は発行元の種別だけで決まる。svc 番号では決めない。**

- 信頼された活性化 → カーネルプリミティブを直接実行
- それ以外 → **トランポリン**。現フレームを退避し、pc を登録済みハンドラへ張り替え、
  呼び出し情報を渡して同一スレッド上でハンドラを走らせる

> **不変条件 I-1**: カーネルは svc 番号で経路を分岐しない。

## 7. カーネル ABI **[設計]**

### 7.1 カーネルが知ること / 知らないこと

**知る**: スレッド / 文脈 / スタック / スタック上限、呼び出しフレームの push・pop、
登録済みハンドラの entry pc と信頼フラグ、スケジューリング機構、MPU region

**知らない**: オブジェクト、オブジェクト ID、メソッド表、export、md、svc ルート

これは P1 (機構と方針の分離) を限界まで押し進めた形。同時に、ISA ごとに書き直す量を
最小化する (オブジェクトモデルは全 ISA 共通の C++ として残る)。

### 7.2 プリミティブ

```
CALL(entry_pc, callee_cookie, caller_cookie, priv, args…) -> err
    現フレームを退避し entry_pc へ制御を移す。cookie は解釈しない。
    失敗 (スタック不足) は err で返す。panic しない。

RETURN(n, value, err, depth_claim) -> err
    n 段 pop。depth_claim = 発行側が申告する「今のネスト数」。
    実際の深さと一致しない限り 1 段も落とさずエラー (§9.3)。

REDISPATCH(entry_pc, callee_cookie, mode) -> err
    現在処理中の syscall を別ハンドラとして実行し直す。
    mode = PUSH (戻ってくる) / REPLACE (戻らない。exit の実装に使う §9.4)

SET_HANDLER(entry_pc)          トランポリンの宛先。信頼活性化からのみ
SWITCH(tid) / GRANT(tid, us)   実行権 (§10)
```

### 7.3 委譲ファミリ

| | 入る ABI | 呼び出し元として渡すもの |
|---|---|---|
| `REDISPATCH` | ハンドラ ABI (元の syscall そのまま) | 元の発行元 |
| `CALL` | メソッド ABI | `caller_cookie` (発行側が指定) |

「元の発行元を渡す (strict)」か「自分を渡す (中継者)」かは**方針**であり、
カーネルの機能ではない。→ **カーネルプリミティブは 2 種で足りる。**

> **不変条件 I-2**: `CALL` を発行できるのは信頼活性化だけ。
> したがって `caller_cookie` の偽装は信頼境界の内側でしか起こり得ない。

> **★ここが §4.2 のアクセス制御の土台。** 呼び出し元 identity が正しく伝わらないと、
> 親子関係も md も検査しようがない。現行実装はここが壊れている (§12.1)。

## 8. 呼び出しフレーム **[実装済]**

### 8.1 退避先はスレッド自身のスタック

共有アリーナを使わない。実際にネストした分しか消費せず、溢れは**スタック上限機構が
消費したスレッドだけを止める** (共有アリーナの枯渇は系全体の停止だった)。

### 8.2 幾何

スタックは下へ伸びるとする。syscall 発行時の SP を `X - fs` とする
(`fs` = 例外フレーム実サイズ。ISA と FP 状態で変わる)。

```
低位 ←                                                            → 高位
[ 呼び先が使う ][ 書き換え用フレーム fs ][ 退避域 total ][ 呼び出し元の生スタック ]
                X-total-fs             X-total        X
                ↑ 復帰に使うフレーム    ↑ 復帰後の SP
```

退避域 `[X-total, X)` の内訳 (低位→高位):
`[ ヘッダ ][ FP レジスタ (has_fp のときだけ) ][ **元の例外フレーム fs** ]`

> **不変条件 I-3**: **元の例外フレームは動かさない。** 退避域の一番上に元の位置のまま
> 入る。下へ複製するのは書き換え用の作業コピーだけ。

> **不変条件 I-4**: 復帰後の SP が退避域に食い込んではならない。ISA が復帰時に SP を
> 追加調整する場合 (例: ARMv8-M の xPSR bit9 による +4)、その分の余裕を見込むこと。
> **見込まないとヘッダを踏み潰し、無言でロックアップする**。

### 8.3 FP

呼び出し元が FP 活性のときだけ枠を予約し `has_fp` を記録。復帰時は立っているときだけ復元。

> **不変条件 I-5**: 幾何は push 時に記録した値を**読み戻して**使う。再計算しない。

## 9. 巻き戻し規約 **[実装済 / exit のみ設計]**

### 9.1 所有権規律

> **不変条件 I-6**: **フレームを push した層が、その層で pop する。**

各層は「自分の 1 枚」だけを落とす。**総数を計算する主体はどこにも存在しない。**

### 9.2 任意段数は異常系専用

`n > 1` が要るのは「フォールト / 予算超過で連鎖を畳む」場合だけ。数えるのは
**連鎖を所有している側**であり、戻る側は関与しない。

### 9.3 段数の検算 (両側チェック)

発行側が「今のネスト数」を申告し、カーネルが実際の深さと突き合わせる。
これは段数の検算であると同時に **I-6 (所有権) の検査**である。

### 9.4 exit は REDISPATCH(REPLACE) で **[設計]**

exit は定義上その先が無いので、置換のコスト (戻り道での処理を失う) が発生しない。
置換にするとフレームが増えず、自己参照 (+1 のずれ) が消え、段数を数える主体も消える。
そして **exit は self-limited** (自分のフレームしか落とせない) なので、
**全オブジェクトに開放しても特権昇格にならない**。

> **注意**: 前方への委譲を REPLACE で行ってはならない。委譲した層が制御を取り戻さず、
> エラーの翻訳・後始末・会計ができなくなる。**既定は PUSH**。

## 10. 資源の委譲 **[実装済 (CPU)]**

### 10.1 1 つの形をすべての軸へ

> **持つ者が貸す / 外側の値でクランプ / スタックに積み戻りで pop /
> 超過は超過した者にだけ当たる (系は死なない)**

| 軸 | 状態 |
|---|---|
| CPU | `GRANT` **[実装済]** |
| メモリ (実行時) | スタック上限機構 = 期限のメモリ版 **[実装済]** |
| メモリ (データ) | オブジェクトごとの arena **[未]** ← 原設計ルール 1・3 |
| 権限 | 貸さない (§11.2) |
| I/O | 優先度付きストリーム **[未]** |

> **不変条件 I-7**: 委譲の期限は**外側の期限でクランプされる**。借りた以上を又貸しできない。

### 10.2 時限は quantum ではない

正常時は期限より十分早く譲るので発火しない。その限り**「譲らない限り処理は原子」という
協調の性質は保たれる**。期限は「1 つの暴走が全系を凍らせない」ための安全網。

## 11. 保護モデル — 3 つの軸に分解する

### 11.0 なぜ分解が要るか

原設計 (2024) の「特権オブジェクト」は、次の 3 つを 1 語に束ねていた。

| 軸 | 決めるもの | 機構 | 2024 での言い方 |
|---|---|---|---|
| **A. 実行特権** | 特権命令 (MPU 設定 / CONTROL / 割り込み制御) を実行できるか | `CONTROL.nPRIV` / RISC-V の U-mode | 「カーネルモードのまま処理」 |
| **B. メモリ到達範囲** | どのアドレスを読/書/実行できるか | MPU region (+ PRIVDEFENA) / PMP / MMU | 「カーネル空間に配置する」 |
| **C. オブジェクト権限** | 誰のメソッドを呼べるか / md を払い出せるか | カーネルオブジェクトが持つ表 (親子関係 / md) | 「全オブジェクトを操作する権利」 |

束ねていた理由は、Linux 的な「カーネル空間 = カーネルモードでしか触れない別領域」を
そのまま借りたため。**MMU を持つ環境では A と B が事実上連動する**ので区別が不要だった。

しかし本設計は**単一アドレス空間**を前提にする (MMU を持たない対象を含む)。
そこでは「カーネル空間に置く」は**場所ではなく保護状態**の話になり、A と B は分離する。
そして C はそもそも CPU の話ですらない — カーネルの外にある表の話である。

### 11.1 単一アドレス空間でも「カーネル空間」は作れる

MMU が無くても、MPU の **PRIVDEFENA** (region で明示していない領域は特権のみアクセス可)
を使えば「非特権実行時には触れない領域」が定義できる。これが単一アドレス空間版の
「カーネル空間」である。

現行実装の Step0 (W^X) が既にこの形になっている **[実装済・実機で有効]**:

- region0: XIP flash 全窓 = RO+X
- region1: `__end__` 〜 SRAM 終端 = RW+XN
- **PRIVDEFENA=1** → region 外 (静的データ / ペリフェラル / SIO) は**特権のみ**

> **したがって「単一アドレス空間だから分離できない」は誤り。** 原設計が
> 「RP2040 には仮想アドレスマッピングが無いので全オブジェクトでアドレス空間を
> 共有するという仕様が必要」と諦めた点は、MPU を持つ対象では乗り越えられる。

### 11.2 軸 A (実行特権) — 要るのはカーネルオブジェクトだけ

特権命令が実際に必要なのは **MPU/PMP を書く主体** と **CONTROL を書き換える主体**
だけ。それはカーネル (と、カーネルオブジェクトの一部) に限られる。

> **不変条件 I-8**: 委譲されたサブハンドラは**一般オブジェクトのまま**走る。
> ハンドラであることは特権を意味しない。

これを破ると、svc ルート表に登録されただけのオブジェクトが `SET_HANDLER` で
系全体の syscall を乗っ取れる。

**ドライバは非特権で走れる。** デバイスレジスタへのアクセスは軸 A ではなく
軸 B (region を開ける) で与える。**「IO を触るから特権」ではない。**

**状態: 機構は実機で検証済み [実装済] (2026-08-17)。**

最小プローブ (`SHIZU_UNPRIV_PROBE`) で確認。**プローブ自身に `MRS CONTROL` を
読ませて自己申告させる**のが要点 (後述の理由)。

| 観測 | 値 |
|---|---|
| 非特権プローブの CONTROL | **`3` = `0b11` (SPSEL=1 + **nPRIV=1**)** |
| 比較用の特権プローブの CONTROL | `2` = `0b10` (nPRIV=0) |
| 生の `svc` による特権往復 | 成立 (毎ループ実行、系は健全) |
| `panic` / `HardFault` | 0 |

### 11.2.0 ★測定の落とし穴 — 「非特権で動いた」は自己申告なしには言えない

最初の計測は **CONTROL=2 (特権のまま)** で走っており、「非特権で動いた」という
観測は**すべて無効**だった。気づけたのは `MRS CONTROL` を読ませたから。

原因: プローブの起動関数は**カーネルオブジェクトとして**走るため、そこから撃った
`svci<SET_OBJECT_UNPRIVILEGED>` (obj_api 24) が「発行元 = カーネルオブジェクト」
判定でプリミティブ側の switch へ入り、**24 は `kernel_object_svc_num` に無いので
`default` で黙って捨てられていた**。

> **★obj_api の呼び出しはカーネルオブジェクトから撃つと無音で消える。**
> カーネルオブジェクト内からは表を直接書くこと。これは ABI の穴であり、
> 新実装では「未知の番号は捨てずにエラーを返す」べき (§14 の方針と一致)。

> **自己テストの原則**: 「非特権で動いた」「委譲が効いた」のような**状態の主張は、
> 対象自身に申告させて突き合わせる**こと。動いたという観測だけでは、
> 意図した状態でなかった可能性を排除できない (§16)。

### 11.2.1 ★2026-07-20 の Step1 失敗は機構の欠陥ではなかった

FLIGHT_CONTROLLER を非特権化した試みは起動直後の HardFault で失敗したが、原因は
**「一番複雑なオブジェクトで機構を試した」ことによる交絡**だった
(svc 委譲を 1 段プローブ抜きに 6 段ネストでいきなり試して原因を絞れなかったのと
同じ方法論の誤り)。

MPU 設定を読むと理由が確定する:

| region | 範囲 | AP | 非特権から |
|---|---|---|---|
| 0 | XIP flash 全窓 | `0b11` = RO 全特権レベル, X | ✅ 読み・実行 |
| 1 | `__end__` 〜 SRAM 終端 | `0b01` = RW 全特権レベル, XN | ✅ 読み書き |
| 2-7 | 無効 | — | — |
| **region 外** | **PRIVDEFENA=1** | — | ❌ **特権のみ** |

そして **`.bss` は丸ごと `__end__` の下**である (実測: `__bss_end__` == `__end__` ==
`0x200390ac`)。したがって非特権オブジェクトは:

- **自分のグローバル/static に触った瞬間にフォールト**する
- ペリフェラル (GPIO / I2C / UART / USB)、**SIO** (`get_core_num()` の CPUID)、
  タイマ (`time_us_64()`) も region 外なのでフォールトする

`printf` はガードされていたが、`get_core_num()` や `time_us_64()`、そして
ドライバ自身のグローバルが残っていた。

> **注意**: 現行 `include/kernel.hpp` の「region1 は unprivileged にも RW を許可して
> いるため、他オブジェクトのスタック/**静的データ**へのアクセス自体はフォールト
> しない」という記述は**誤り**。スタックは malloc 産なので当たっているが、
> 静的データは `__end__` の下なのでフォールトする。

### 11.2.2 実オブジェクトを非特権化する条件

したがって「非特権で動くオブジェクト」の要件は:

1. **private global を `.bss` から出す** → **オブジェクトごとの arena (ヒープ上)** へ。
   arena は region1 に入るので自動的に非特権アクセス可能になる (§10.1 / §12.5)
2. ペリフェラルは軸 B で個別に region を開ける (§11.3)。**「IO を触るから特権」ではない**
3. 標準ライブラリを直に呼ばない (内部でペリフェラルや特権命令に触れる)

### 11.2.3 速度 — 非特権に実行コストは無い [実測]

同一実行・同一クロックで、**まったく同じコードを非特権と特権で並走**させた A/B:

| | 2 秒あたりのループ数 | 比 |
|---|---|---|
| 非特権 (CONTROL=3) | 37,197 | **100.00%** |
| 特権 (CONTROL=2) | 37,197 | (基準) |

6 ラウンド連続で差は 0〜3 カウント (最悪 99.99%)。ARMv8-M では MPU チェックが
メモリパイプラインに入っていて特権/非特権で同じ経路を通るので、構造的にも妥当。

> **「開発は非特権、本番は特権で高速化」という戦略は成立しない (速度差が無い)。**
> 裏を返せば**常時非特権で走らせても遅くならない**ので、本番も非特権のままでよい。
> §11.5 (性能のために特権を配る理由が消えた) をさらに強める結果。

**未測定**: (a) フォールトが実際に起きたときのコスト (例外エントリ + ハンドラ + 復帰)、
(b) region を per-object に切り替える場合の `CALL`/`RETURN` ごとの MPU 書き込みコスト
(§11.3)。後者は非特権化を実用化するときに測ること。

### 11.2.4 違反時のハンドリング [実測]

MemManage を有効化 (SHCSR.MEMFAULTENA) してハンドラを置けば、**違反しても系は止まらない**。
プローブでは SIO CPUID (`0xd0000000`) への非特権ストアが正しくフォールトし、
`MMFAR` にアドレス、スタックフレームから PC が取れ、**命令をスキップして続行**できた
(578 回連続、`panic` ゼロ)。

- **ストア**: 書き込みが落ちるだけ = 実質「0 埋め」と同じ意味論
- **ロード**: 行き先レジスタが**元の値のまま残る** (0 にはならない)。0 埋めするには
  命令デコードして Rt を特定する必要がある — 本実装での課題

**測定対象と記録先は必ず分けること。** 最初の版は違反対象に記録用変数自身を指定して
しまい、値が潰れて計測が壊れた。また `.bss` 末尾は `__end__` の 32B 切り上げで
region1 に入り込み得るので、違反対象には **region0/1 に絶対入らないアドレス**
(SIO 等) を使う。読み出し専用レジスタなら万一通っても副作用が無く安全。

**1 が本命**で、これは既に記録済みの「ドライバの private global を per-object arena へ
移す」方向と一致する。**非特権化は arena の実装に依存する** — 順序を間違えると
また複雑なオブジェクトで交絡した実験をすることになる。

### 11.3 軸 B (メモリ到達範囲) — per-object に切り替える

MPU region 数は少ない (ARMv8-M で 8 程度) が、**全部を per-object にする必要はない**。
共通部分を固定し、可変部分だけを呼び出しのたびに差し替える:

| region | 内容 | 切り替え |
|---|---|---|
| 0-1 | W^X (XIP RO+X / heap RW+XN) | 固定 |
| 2-3 | **現在オブジェクトの private arena** | CALL/RETURN で切り替え |
| 4-5 | **現在オブジェクトに開かれたデバイス窓** | 同上 |
| 6-7 | 予備 (共有ストリームバッファ等) | |

切り替えは MPU レジスタを数本書くだけで、コンテキストスイッチより桁で安い。
**同一スレッド上のメソッド呼び出しという実行モデル (§6.1) と相性が良い** —
どうせ `CALL` で特権と cookie を差し替えるので、そこに region set を足すだけ。

→ `CALL(entry_pc, callee_cookie, caller_cookie, **protection**, args…)`
   (`protection` = 実行特権 + region set)

**会計との関係**: region 数の制約があるので、**保護の単位と会計の単位を分ける**。
会計はオブジェクト単位 (安いので細かくできる)、保護はサブシステム単位
(region に収まる粒度でグループ化)。

### 11.4 軸 C (オブジェクト権限) — CPU の特権とは無関係

「誰のメソッドを呼べるか」「md を払い出せるか」は**カーネルオブジェクトが持つ表**の話。
CPU の実行特権とも、メモリ到達範囲とも独立している。

> **System Object は軸 C だけを持てばよい。軸 A も軸 B も要らない。**

これは §4.2 のアクセス制御そのもの。そして権限は静的クラスで表さず、貸し出しもしない
(§11.6)。

### 11.5 ★2024 が特権を与えていた理由は消滅している

原設計は「高速化のために IO を操作するオブジェクトだけ特権オブジェクトにする」と述べ、
その代償として**システム全体をクラッシュさせるリスクを明示的に受け入れて**いた
(「カーネル空間に配置している以上避けられない。慎重に運用すれば問題ない」)。

根拠は「特権オブジェクトのメソッド呼び出しは**コンテキストスイッチせずに関数呼び出しで
済む**」という点にあった。

**しかし本設計では、すべてのメソッド呼び出しが同一スレッド・同一スタックの保護された
サブルーチン呼び出し (§6.1) なので、そもそもコンテキストスイッチが発生しない。**

→ **速さは特権と無関係になった。** したがって:

- **性能を理由に特権を配る必要がない**
- 2024 が受け入れていた「特権ドライバが系ごと落とす」リスクを**受け入れる理由も無い**
- 特権は「本当に特権命令が要る主体」だけに限れる (§11.2)

これは §14 (オブジェクトの誤りで系を落とさない) とも整合する。原設計の妥協点が
1 つ、実行モデルの変更によって不要になった。

### 11.6 権限は貸さない **[設計]**

サブカーネルに軸 A を渡さず、カーネルオブジェクトを往復する overhead を払う。
高頻度パスは元々 syscall の外にある (§13) ので実害が小さく、
**サブカーネルが資源を使い潰せると会計が成立しない**。

静的な信頼クラスの enum を足すのはリングモデルであり、カーネル内に権限マトリクスを
作って P1 を壊す。将来必要になった場合の唯一の正しい拡張方向は「クランプ付きの
貸し出し」(§10 と同型) であって、クラスの追加ではない。

なお**軸 B は貸し出しに近い形になる** — `CALL` のたびに呼び先の region set を渡し、
`RETURN` で自動的に戻る。これは §10 の「積んで戻りで pop」と同型で、矛盾しない。

## 12. ★原設計 (2024) との差分 — 失われているもの

現行実装は機構としては原設計より進んでいるが、**アクセス制御の中核が丸ごと欠けている**。

### 12.1 呼び出し元 identity が伝わらない [重大]

現行の `METHOD_CALL` は呼び出し元をカーネルオブジェクトに化けさせる
(callee が受け取る「呼び出し元 ID」が常に 0 になる)。したがって:

- **オブジェクトが自前のアクセス制御を持てない**
- 親子関係も md も**検査のしようがない**
- 資源を「誰の勘定に付けるか」も決められない

→ §7.3 の `caller_cookie` はこれを直すための設計。**原設計の 4.2 を復活させる前提条件。**

### 12.2 親子関係が存在しない [重大]

原設計ルール 5・8 (親子関係 + 親子のメソッドのみ呼べる) が実装されていない。
オブジェクト表に親を表す情報がなく、**任意のオブジェクトが任意のオブジェクトの
export メソッドを呼べる**。

これは §1.2 で批判した「マイクロカーネルの無秩序」と**同じ状態**である。
現行実装は、批判した対象に自分が戻ってしまっている。

### 12.3 md — 所在は「カーネルオブジェクト」で決定 (2026-08-17)

**md_table はカーネルオブジェクトが抱える。** これは妥協ではなく構造上の正解:

- **§7 の帰結として自然**。カーネルがオブジェクトを知らない以上、オブジェクトモデルの
  表 (`object_table` / メソッド表 / svc ルート表) は全部カーネルオブジェクトが持つ。
  **md も同種であって例外ではない** (「方針が予算免除ゾーンに入る」という懸念は過剰
  だった — 既に同じゾーンにルート表がある)
- **性能上の根拠がこの配置でだけ成立する**。カーネルオブジェクトが md → (obj, method)
  を解決して**そのまま `CALL` を撃てる**ので 2 段目のトランポリンが要らない。
  System Object に置くと解決のための往復が増え、償却という売りが消える

→ **md は「カーネルオブジェクトの svc ハンドラ API」として実装する。**
   `ktab_lock` (§14.5) の保護対象にも含める (カーネルオブジェクトが持つ共有表なので)。

### 12.3.1 直すべきなのは配置ではなくアクセス制御

原設計では md は「親子関係というデフォルト拒否からの、特権オブジェクトによる明示的な
許可」だった。現行実装は:

- 呼び出し元索引ではなく**引数で索引を指定**する → 誰でも他人の md を書き換えられる
- 払い出しに権限検査がない
- `method_id` が常に 0 で埋まる (未完成)
- 利用者ゼロ

**親子関係 (§12.2) が無いためデフォルト拒否が存在せず、md が「例外」として意味を持てない。**
だから md は「性能上の意味も無い遅い経路」に見えていた。**md 単体を直しても意味がなく、
12.1 → 12.2 → 12.3 の順に戻す必要がある。**

直す内容は 3 つ (配置は変えない):
1. **索引を呼び出し元ごとに** (`md_table[caller][slot]`)。現行は引数で索引を指定するので
   誰でも他人の md を書き換えられ、呼び先をすり替えられる
2. **払い出しの権限検査**。カーネルが記録した**偽装不能な発行元** (§7.3 の
   `caller_cookie` / 現行の r5) で判定する
3. **デフォルト拒否 (親子関係) を先に入れる**。無いと md が「例外」として意味を持たない

### 12.4 スレッド生成モデルの意図的な変更

原設計は「メソッド呼び出しごとにカーネルがスレッドを作る」だったが、現行は
**同一スレッド・同一スタック上の保護されたサブルーチン呼び出し**である。

これは意図的な変更で、呼び出しコストが桁で下がる。ただし原設計が
「イベント待ちのコードを書かなくてよい」根拠にしていた性質 (§4.3) は、別の形で
再導出する必要がある:

- 非同期起動 (`async_call`) — 呼び出しごとではなく、オブジェクト起動時に 1 本
- ストリーム (§13) — 高頻度イベントは syscall を通さない

### 12.5 資源の解放 (ルール 3) が無い

オブジェクトが自身の資源を解放する手段がない。原設計はホットプラグ (USB デバイスが
外れたらドライバオブジェクトごと消してメモリを解放) を想定していた。
§10.1 の「メモリ (データ)」軸が埋まると自然に実装できる。

## 13. ストリーム **[実装済]**

**データプレーンは syscall を通らない。** push/pop は共有リングに対するライブラリ操作。
カーネルが関与するのは制御プレーン (登録 / discovery / バインド) だけ。

`connect(src, dst)` は 2 つのストリームをカーネル専有 DMA で直結し、中間オブジェクトの
コピーを丸ごと消す。DMA チャネルはオブジェクトへ渡さない (DMA は MPU を素通りするため)。

> この設計があるので §11.2 の「overhead を払う」判断が成立する。

## 14. エラー方針 **[実装済]**

> **不変条件 I-9**: **オブジェクトの誤りで系を落とさない。**

段数の申告ミス、スタック不足、不正な呼び先、深すぎるネスト — すべてエラー復帰。
巻き戻せない活性化は記録を残して**当該スレッドだけを隔離**する。
panic は「カーネル自身の不変条件が壊れた」場合に限る。

これは §10 の「超過は超過した者にだけ当たる」をエラー処理へ適用したもの。
そして **目標 1 (アプリ側が配慮を欠いていても運用で解決可能)** の実装形でもある。

## 14.5 共有状態の同期規約

資源の委譲 (§10) は「持つ者が貸す」形だが、**カーネルが持つ共有表の一貫性はその軸に
乗らない** (誰かから借りるものではない)。別の規約が要る。

### 14.5.1 1 コア内の相互排除は無償で手に入る

例外優先度を **svc 最優先 > タイマ > 切替 (最低)** に置き、**スレッド切替は最低優先度の
遅延例外でのみ起こす**。すると:

- svc ハンドラ実行中はタイマにも切替にも割り込まれない
- ハードウェア IRQ に割り込まれても、切替は最低優先度の例外を pend するだけなので
  **ハンドラを抜けるまで走らない**

→ **svc ハンドラの中にいる = そのコアではスレッドが切り替わらない。**
取得コストゼロ、取り忘れ・解放忘れが原理的に起こらない。ロックより強い。

> **★これは ARM の例外優先度モデルに依存している。** 移植時に静かに失われるので、
> `arch` の要件として明記すること (§5.1): 「切替は最低優先度の遅延例外でのみ起こす」。

### 14.5.2 コア間は明示的な保護が要る

per-core / per-thread の状態は claim (§7.2 の実行権) により**単独所有**なのでロック不要。
**ホットパス (`CALL` / `RETURN`) は per-thread の状態しか触らない。**

ロックが要るのは**コア間で共有する表**だけ: オブジェクト表 / メソッド表 /
svc ルート表 / **md** / ストリーム登録表。いずれも変更は低頻度 (生成・登録・bind) なので
**1 本の短いスピンロック (ktab_lock) で足りる**。

規律:
- **例外文脈なのでブロックも yield もできない** → 純粋なスピンにする
- **yield を跨いで保持しない**。跨ぐと保持したまま他スレッドへ渡り自明にデッドロック
- 実装は §14.5.3 の継ぎ目を通す

### 14.5.3 ★アトミックは arch の継ぎ目

「CAS がある」こと自体が移植性の仮定である。同一ベンダの 2 チップで答えが真逆になる:

| | マルチコア atomic の手段 |
|---|---|
| **RP2350 (ARMv8-M)** | LDREX/STREX。**SIO ハードウェアスピンロックは erratum で使用不可** |
| **RP2040 (ARMv6-M)** | **LDREX/STREX がそもそも無い**。SIO スピンロックを使うしかない |

→ アトミック操作 (枠取りの CAS、ktab_lock) は **`arch` テンプレートのパラメータ**として
外から与える。現行実装では `arch_claim_thread_slot()` が唯一の継ぎ目として括り出してある。

**実バグの例 [修正済 2026-08-17]**: スレッド枠の空きスキャンが「見てから作る」に
なっており、2 コアが同じ枠を観測すると片方が二重初期化検査で **panic して系ごと落ちて
いた** (I-9 違反)。`UNINITIALIZED → RESERVED` の CAS で予約する形に修正。

## 15. 不変条件の一覧

| # | 内容 |
|---|---|
| I-1 | カーネルは svc 番号で経路を分岐しない |
| I-2 | `CALL` を発行できるのは信頼活性化だけ |
| I-3 | 元の例外フレームは動かさない |
| I-4 | 復帰後の SP が退避域に食い込まない |
| I-5 | 幾何は記録値を読み戻して使う。再計算しない |
| I-6 | フレームを push した層が、その層で pop する |
| I-7 | 委譲の期限は外側の期限でクランプされる |
| I-8 | ハンドラであることは特権を意味しない |
| I-9 | オブジェクトの誤りで系を落とさない |

## 16. 自己テストとして必ず持つもの

破っても静かに壊れる不変条件は自己テストで守る。

| 対象 | テスト |
|---|---|
| I-4 / I-5 (幾何) | FP 有無の両方で往復させる |
| I-6 (所有権) | **1 段の最小プローブ → N 段ネスト**の梯子。いきなり多段を試さない |
| **identity の伝播** | ネストの各層で「誰に呼ばれたか」を突き合わせる。**これが無いと §12.1 のような「黙って化ける」バグを検出できない** |
| **状態の自己申告** | 「非特権で動いた」「委譲が効いた」等の**状態の主張は対象自身に申告させて突き合わせる** (例: `MRS CONTROL`、`clock_get_hz`)。動いたという観測だけでは意図した状態でなかった可能性を排除できない (§11.2.0 で実際に誤認した) |
| **カウンタは期待値と突き合わせる** | **前進しているか**だけを見ない。**生存カウンタは機能の証拠にならない** — 実例: CYW43 が死んでも `ble_poll` (ポーリング回数) は前進し続け、壊れていたのは `evt` (実イベント) の方だった (68 → 1)。「出たら悪いもの」の監視だけでは**「出るべきものが出ていない」を捕まえられない** |
| **アクセス制御** (§4.2 復活後) | 親子でない相手を呼んで**拒否されること**を確認する。許可のテストだけでは無意味 |
| I-9 | 意図的に不正な段数を申告し、系が生存することを確認 |

さらに、系が固まっても診断が出る経路 (タイマ割り込みからの同期排出など) を最初から
用意すること。無いと「無言で固まる」の原因究明が成立しない。

## 17. 実装順序の含意

§12 から、**アクセス制御の復活には順序がある**:

1. **`caller_cookie` で identity を伝える** (§7.3, §12.1) ← すべての前提
2. **親子関係を導入し、既定を「親子のみ呼べる」にする** (§12.2)
3. **md を権限付与機構として作り直す** (呼び出し元索引 / 特権オブジェクトのみ払い出し可) (§12.3)
4. オブジェクト arena で資源の保有と解放を実装 (§10.1, §12.5)

1 を飛ばして 2 や 3 をやっても検査が成立しない。3 を単独でやっても
「デフォルト拒否」が無いので意味を持たない。
